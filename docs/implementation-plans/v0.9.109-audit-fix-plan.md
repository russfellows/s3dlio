## 1. Guiding principles

Six principles govern the ordering and test design. A reviewer disagreeing with any of them should attack it here first, before the phase-by-phase plan.

**P1 — Data integrity before everything else.** Any bug that can cause a caller to receive `Ok(...)` while server-side state is wrong or the returned bytes are corrupt ships in the first phase and blocks the release. Correctness > perf > features (per s3dlio's own [CLAUDE.md](../../CLAUDE.md) stability section).

**P2 — Wrong-data-returned is worse than wrong-error-returned.** A caller that gets the wrong bytes with `Ok` cannot recover. A caller that gets an unexpected error can retry or bail. When forced to pick, we prefer to bail loudly over returning silently-corrupt data. This is why 2.1 (short-read corruption) ships before 2.8 (zero-size bail); both are correctness bugs but the failure modes are asymmetric.

**P3 — Test infrastructure is shared, so bugs that use the same test harness cluster together.** Multipart lifecycle (Issue 1) needs a mock S3 client that can inject `AbortMultipartUpload` failures. Range engine (Issue 2) needs a mock `get_range` that returns short chunks or specific error patterns. These harnesses get built once and reused across every bug in that area — so we don't interleave issues that need different infrastructure.

**P4 — Every fix lands with a test that provably fails against the pre-fix tree.** Per the RED-then-GREEN rule ([parent CLAUDE.md](../../CLAUDE.md#6-every-bug-fix-uses-red-then-green-test-driven-verification)). RED is not optional — a test that can't be made to go RED against unmodified code is not yet a regression test.

**P5 — GREEN passing is necessary but not sufficient — the plan spells out where.** Some bugs are inherently only partially testable in a unit-test framework (real backend races, real Python GC timing, real Azure GC window, real network flakes). Where that is the case, the per-bug section calls it out explicitly and proposes a live-test or fault-injection supplement. A reviewer should confirm those adequacy claims are honest, not glossed over.

**P6 — Dependency-aware ordering: fix pre-requisites first.** For example, the Python-side "MultipartUploadWriter used without try/finally" (3.7) becomes materially safer once the Rust-side abort_on_drop and abort_blocking bugs (1.1 + 1.2) are fixed. So we sequence 1.1/1.2 before 3.7. All such dependencies are listed in the per-bug table.

## 2. Ordering rationale — six phases

Phases are ordered by escalating "cost of leaving unfixed" combined with implementation-and-test dependencies (P3, P6). Within a phase, the specific bug order is determined by dependency and by shared test harness. Phase A ships as v0.9.109. Everything else can ship as v0.9.109 or a follow-up v0.9.110, at your call.

| Phase | Name | Bugs | Rationale |
|-------|------|------|-----------|
| **A** | Silent data corruption (release blocker) | 4 | Any of these can silently commit wrong bytes or lose objects while caller sees Ok. Must ship in v0.9.109. |
| **B** | Wrong data returned to caller | 12 | Caller-visible wrong output but at least the wrong-ness is deterministic (unlike Phase A). Should ship in v0.9.109; skippable to v0.9.110 only for the low-severity subset. |
| **C** | Silent failure elimination | 6 | Real failures presented as success bools / empty lists / False returns. Loses operator signal. Should ship in v0.9.109. |
| **D** | Backend correctness / hygiene | 9 | Real bugs but with narrower blast radius (specific backends, specific configs, specific edge cases). |
| **E** | Edge cases / low severity | 4 | Reachable only with adversarial inputs or unusual configs. |
| **F** | Env vars / config-ignored, plus one docs fix | 4 | Same failure class as mlp-storage#715 — user config silently no-ops. Includes the one pure-docs bug (7.2 / Environment_Variables.md self-contradiction) since it's the same subject area. |

**Total: 39 items across 6 phases.**

**Recommendation:** ship Phase A + B + C in v0.9.109 (22 bugs). This is a large PR but the bugs are cleanly categorizable, share test harnesses, and every fix has an independent test. Ship Phase D + E + F as v0.9.110 same session, immediately following v0.9.109. If Phase A+B+C implementation runs long, split as A + selected-B for v0.9.109 (data-integrity + Phase 4 retry regression) and the rest for v0.9.110 — see §10 for the concrete split.

## 3. Phase A — Silent data corruption (release blocker, 4 bugs)

Everything here can silently produce wrong on-server state or corrupt bytes with `Ok` at the caller. Any of these getting into a training run or checkpoint write is a real corruption event.

### A1 · Bug 2.1 · Range engine short-read silent corruption 🔴 CRITICAL

**File:** `src/range_engine_generic.rs:431` (assembly cursor) and `:363-372` (short-read warn-not-error).
**What it is:** `download_with_ranges` assembles chunks with `write_offset += bytes.len()`. A non-final short read shifts all subsequent ranges to wrong offsets and truncates the tail. The engine only emits `tracing::warn` on short reads; the returned `Ok(Bytes)` contains corrupt data. The S3-specific `concurrent_range_get_impl` (`s3_utils.rs:1359-1367`) already has the correct `bail!` guard — this generic engine (used by Azure/GCS/file/direct) is missing it.

**Contract decision for v0.9.109 (locked before test write):** any detected short read returns `Err` naming the range's offset, expected length, and actual length. **No "tolerate and reassemble"** option — reassembly cannot be safe when a chunk is short, because the running cursor design cannot know where the missing bytes belong. This lines up with the S3 path's existing `bail!("range short read: ...")` guard. Same policy applies to over-read (chunk returns MORE bytes than requested) — `Err`, don't attempt to place them. Also applies when the sum of chunk lengths does not equal the pre-declared `object_size` — `Err` with a message noting the size drift.

**RED test plan:**
1. Add `tests/test_range_engine_short_read.rs`.
2. Build a mock `ObjectStore` whose `get_range` returns a shortened chunk for range index 1 of 4 (e.g. 512 KiB instead of the requested 1 MiB) but full-size for ranges 0, 2, 3.
3. Call `RangeEngine::download` with `min_split_size` low enough to activate the engine for a 4 MiB payload.
4. Assert: return is `Err` whose message contains `"short read"`, the range offset (`0x100000` or similar), the expected length (`1048576`), and the actual length (`524288`).
5. Verify: run against unmodified HEAD → returns `Ok(Bytes)` → assertion fails. Run against fix → returns `Err` → assertion passes.
6. **Additional cases** (same test file, separate `#[tokio::test]` functions):
   - Over-read: chunk returns 1.5 MiB for a 1 MiB range → `Err` with `"unexpected excess"` message.
   - Size drift: sum of chunk lengths ≠ declared `object_size` → `Err` with `"declared size"` message.

**GREEN adequacy:**
- ✅ Deterministic mock-based RED-then-GREEN cleanly proves the specific fix.
- ✅ Contract is locked in this document, not deferred to implementation. Test text is unambiguous.
- ⚠️ **Cannot prove** we detect every short-read pattern in production. Real S3-compatible backends may drop bytes in ways the mock doesn't (e.g. mid-stream chunked-encoding truncation on a real socket). See §11 for the live-test gate — **not a v0.9.109 blocker**, targeted for v0.9.110.

**Dependencies:** None. Standalone fix.

**Estimated blast radius of the fix:** medium. Any caller currently relying on the silent-truncate behavior (unlikely but possible in some test paths) will now see errors. Grep confirms no callers depend on the truncation.

### A2 · Bug 1.1 · `abort_on_drop=false` silently commits partial data

**File:** `src/multipart.rs:156` (Drop impl), `:563` (coordinator loop), `:672` (Complete call).
**What it is:** When `abort_on_drop=false`, dropping the sink without `close()`/`abort()` still causes the coordinator to `CompleteMultipartUpload` with whatever parts it has, silently producing a truncated object with a valid ETag. Docs and README say abort_on_drop=false means "leave the MPU dangling" — code says "commit whatever we have".

**Contract decision for v0.9.109 (locked before test write):** **best-effort abort on drop, regardless of the `abort_on_drop` flag value.** Concretely: Drop cancels the coordinator (so it never calls Complete), then fires an `AbortMultipartUpload` (fire-and-forget spawned task) on the S3 side. If the abort fails, a `tracing::warn!` records the blob key and upload_id so an operator can clean up manually. Docs and README are updated in the SAME release to describe `abort_on_drop` as **no longer a functional switch** — it now controls only whether the fire-and-forget Abort is spawned or skipped; **the coordinator is always cancelled on drop.** The old "leave dangling" interpretation was already unreachable in code (drop closes `part_tx`, and closed channel currently triggers Complete anyway); we replace the ambiguity with an explicit best-effort-cleanup guarantee. `abort_on_drop=true` (default) → cancel + fire Abort + warn on Abort failure. `abort_on_drop=false` → cancel + no Abort → operator explicitly opts into the dangling-upload cost.

**RED test plan:**
1. Add `tests/test_multipart_abort_on_drop_false.rs`.
2. Mock S3 client: stub `create_multipart_upload`, `upload_part` (3 parts), `complete_multipart_upload`, `abort_multipart_upload`. Track which is called and in what order.
3. Case A (`abort_on_drop=true`, the default): build `MultipartUploadWriter`, write 3 parts, drop without `finish()`. Assert: `complete_multipart_upload` was **never** called; `abort_multipart_upload` **was** called exactly once.
4. Case B (`abort_on_drop=false`): same as A but with `abort_on_drop=false`. Assert: `complete_multipart_upload` was **never** called; `abort_multipart_upload` was also **not** called (operator chose to leak).
5. Case C (`abort_on_drop=true`, transient abort failure): stub `abort_multipart_upload` to return Err. Same drop scenario. Assert: `complete_multipart_upload` never called; `tracing::warn!` fired at least once naming the upload_id.
6. Verify RED against pre-fix code → Case A and Case B both call `complete_multipart_upload` → assertions fail.

**GREEN adequacy:**
- ✅ Fully deterministic. Contract locked in this document.
- ✅ Doc + code changes ship together in the same PR (per contract) — no separate release for the doc update.
- ⚠️ Behavior change flagged in changelog under "Behavior changes": `abort_on_drop=false` no longer silently commits partial data; it now leaves the MPU dangling as originally documented.

**Dependencies:** Coupled with A3. Coordinator cancellation is the shared mechanism.

### A3 · Bug 1.2 · `abort_blocking()` swallows error, then coordinator commits partial data

**File:** `src/multipart.rs:468-488`.
**What it is:** `abort_blocking()` discards the `AbortMultipartUpload` result via `let _ = ...` and returns `Ok(())` unconditionally. If the abort request fails transiently, the `upload_id` remains valid on the server. Struct then drops, `part_tx` closes, coordinator sees channel-closed and calls `CompleteMultipartUpload` — silently committing partial data even though the caller requested abort.

**Contract decision for v0.9.109 (locked before test write):** consistent with A2. `abort()` and `abort_blocking()` **always cancel the coordinator** (so Complete is never issued) and **always return `Ok(())`** to the caller — the caller asked to abort, and the semantic promise is "we will not complete this upload". The S3-side AbortMultipartUpload is best-effort: fire the request, and on any failure emit a `tracing::warn!` naming the blob key, upload_id, and the underlying error. This matches the S3 SDK's own idempotency model (abort is a hint, not a hard requirement — server-side MPUs are GC'd after a bucket-lifetime window if not explicitly cleaned up). The alternate contract (returning `Err` on transient AbortMultipartUpload failure) is explicitly rejected because it couples caller error-handling to network flakiness of a cleanup operation the caller cannot re-attempt anyway.

**RED test plan:**
1. Add `tests/test_multipart_abort_blocking.rs`.
2. Mock S3: stub `abort_multipart_upload` to return `Err(TransientNetworkError)`. Stub `complete_multipart_upload` to succeed if called (must NOT be called).
3. Build `MultipartUploadWriter`, write 2 parts, call `writer.abort()`.
4. Assert: (i) `abort()` returns `Ok(())`; (ii) `complete_multipart_upload` was never called; (iii) `abort_multipart_upload` was called exactly once; (iv) at least one `tracing::warn!` naming the upload_id was emitted (use `tracing-test` crate or capture layer).
5. Case B: same setup but `abort_multipart_upload` succeeds. Assert (i)+(ii)+(iii); assert no warn was emitted.
6. Verify RED: pre-fix Case A leaves `complete_multipart_upload` called (assertion (ii) fails).

**GREEN adequacy:**
- ✅ Deterministic. Contract locked.
- ✅ Test asserts on the observable warn — matches "operator can find and clean up" contract from A2.
- ⚠️ **Coordinator cancellation mechanism (implementation-only):** either `CancellationToken` on the coordinator, `PartMsg::AbortRequested`, or a shared `aborted` flag. Fixer's choice. Test asserts on the outcome (Complete never called), not the mechanism.
- ⚠️ **Real transient-network-failure path** — a hyper test server returning 503 on `POST ?uploads=...abort=` is a more faithful test. See §11: **not a v0.9.109 blocker**, targeted for v0.9.110.

**Dependencies:** Coupled with A2. Same PR, shared coordinator-cancellation mechanism.

### A4 · Bug 4.5 · `delete_objects` ignores S3's per-object error list

**Files:** `src/s3_ops.rs:353` and `src/s3_utils.rs:1596-1602`.
**What it is:** S3's `DeleteObjects` returns HTTP 200 with a body containing `Errors=[{Key, Code, Message}, ...]` for objects that couldn't be deleted. Both call sites match `Ok(_)` and return `Ok(())` without inspecting `.errors()`. Caller believes the batch succeeded.

**Contract decision for v0.9.109 (locked before test write):** keep the current `Result<()>` return shape. On non-empty `.errors()`, return `Err(anyhow!(...))` naming the failed keys and their S3 error codes in the message. This is the minimum-risk fix — no signature changes, no caller updates, no ripple across the tree. **Explicitly deferred to a follow-up:** the richer `{deleted: Vec<String>, errors: Vec<DeleteError>}` struct return is a public API redesign; it belongs in a later release with its own migration note, not in the release-blocker phase.

**RED test plan:**
1. Add `tests/test_delete_objects_errors.rs`.
2. Mock S3 client: stub `delete_objects` to return `DeleteObjectsOutput` with `deleted=[]` and `errors=[Error{key: "x", code: "AccessDenied", message: "..."}]`.
3. Call `S3Ops::delete_objects` (and `s3_utils::delete_objects_async`) with `keys=["x"]`.
4. Assert: return is `Err` whose message contains the string `"x"` and the code `"AccessDenied"`.
5. Verify RED: pre-fix returns `Ok(())` → assertion fails.

**GREEN adequacy:**
- ✅ Deterministic. Both call sites can be covered by the same test parameterized on the entry point.
- ✅ Contract is locked in this document, not deferred to implementation.
- ⚠️ Caller-side behavior change: any caller that ignored the previous `Ok(())` and assumed the batch was atomic will now see errors it did not see before. This is an intentional and correct change — the previous silent success was the bug. Flag in the changelog under "Behavior changes".

**Dependencies:** None. Small enough to bundle with 5.3 (GCS delete_objects panic accounting) since both are "delete didn't fully happen but caller sees Ok".

### B9 · Bug 3.10 · Python `_select_endpoint_via_strategy` PID-hash pretending to be round-robin

3. `least_connections` continues to fall back to `round_robin` (it was always a TODO); no change in behavior, but the fallback message now surfaces via logging.

This means `use_mpi_endpoint_distribution=true` and `round_robin` collapse to the same code path when rank vars are available. Document that in `s3dlio_storage.py`'s docstring — the flag becomes vestigial but harmless.

**RED test plan:**

4. Test C (random): monkey-patch `random.seed` recorder; assert seed value derives from rank-if-available or pid-otherwise.
5. Verify RED: pre-fix, Test A fails because `pid % N` is used regardless of rank var, so Counter is uneven.

**GREEN adequacy:**
- ✅ Deterministic for the rank-present case (Test A) — the contract we actually care about, since MLPerf runs always set MPI rank.

## 10. Ship plan and PR strategy

**Option 1 — Single monolithic PR for v0.9.109 (Phase A+B+C, 22 bugs).**
- Pro: one atomic release. All data-integrity + wrong-data + silent-failure bugs closed together.
- Con: PR is large. Review latency and hunk conflict risk grow.

**Option 2 — Three PRs for v0.9.109 (Phase A / Phase B / Phase C, staged over ~1 week).**
- Pro: incremental review, easier bisect, cleaner rollback if any single group has issues.
- Con: coordination overhead. Version stays at 0.9.109 across three merges until final one triggers the release.

**Option 3 — Recommended: two PRs for v0.9.109.**
- PR 1: Phase A (4 bugs) + Phase B critical subset (B1/2.2, B2/2.3, B3/2.4, B5/3.6, B7/4.4 — 5 bugs) — the release-blocker set (**9 bugs**).

- v0.9.109 tag cuts after PR 2 merges.

- **F4 (7.2)** — Pure docs change; testing is grep-based or eye-only.

### 11.1 Release gate — v0.9.109 tag cut

**RED/GREEN unit coverage is SUFFICIENT for v0.9.109 tag cut. Live/fault-injection supplements are NOT release-blockers for v0.9.109.** Rationale:

- The RED/GREEN mock-based tests are what proves each specific bug is fixed. That's the meaning of "regression test" per parent [CLAUDE.md §6](../../../CLAUDE.md).
- Live and fault-injection tests broaden coverage to failure modes the mock doesn't reproduce; they do not (and cannot) prove the fix is *complete*. Their absence is a coverage gap, not a correctness gap.
- Monotonic improvement argument: pre-v0.9.109, users had zero test coverage of these paths. Post-v0.9.109, they have deterministic mock-based coverage. Post-v0.9.110, they will additionally have live-backend coverage. No user is left worse off by shipping v0.9.109 with unit coverage only.

**Concretely, this means the following six supplemental tests target v0.9.110, not v0.9.109:**

| Test | For bug | Kind | Rationale for v0.9.110 timing |
|------|---------|------|-------------------------------|
| Live short-read against MinIO with connection-kill helper | A1 / 2.1 | Live | Requires the MinIO fixture in `tests/live/` to be extended with a mid-body-FIN mode |
| Live transient-AbortMultipartUpload against hyper test server | A3 / 1.2 | Fault-inject | New hyper test server needed under `tests/live/hyper_test_helpers.rs` (H3) |
| Parameterized B1 caller coverage (`data_loader/s3_bytes.rs`, `object_store.rs:1278`) | B1 / 2.2 | Unit (extended) | Needs the parameterized-caller test harness; small, can slip if needed |
| Injectable delete-fn for C5 panic simulation | C5 / 5.3 | Unit (harness) | Needs a small API change to `google_gcs_client.rs::delete_objects` |
| `tokio::time::pause` timing verification for D1 | D1 / 5.1 | Unit | Already targeted for v0.9.110 (Phase D) |
| Live 50k-block cap validation (E3) | E3 / 1.6 | Live | Only meaningful with real Azure; low priority, can slip to v0.9.111 if needed |

### 11.2 Release gate — v0.9.110 tag cut

**Live/fault-injection supplements are NOT v0.9.110 blockers either.** They ship in v0.9.110 or slip to v0.9.111 per the same rule. The v0.9.110 hard gate is: Phase D + E + F unit-test RED/GREEN coverage (17 bugs), plus any items slipped from v0.9.109. Everything else is coverage broadening.

## 12. Risks the plan does not solve

- **Concurrent Python GC pressure** — 3.7 and A2's cleanup safety depend partly on Python's GC timing, which we can influence but not fully control.
- **Real backend behavior variance** — AIStore / MinIO / Ceph / real S3 all have subtle response-header differences that our mocks won't reproduce. Live integration tests catch a subset.
- **Deferred v0.9.110 slippage** — If Phase D/E/F don't ship by the end of day 2, the "fix everything across these two releases" premise weakens. Hard cutoff: anything not fixed by the v0.9.110 tag moves to explicit v0.9.111 tracking.
