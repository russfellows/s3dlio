# s3dlio v0.9.110 Release Notes

**Multi-agent bug audit fix release — 39 fixes across 6 phases, closing issues [#151–#157](https://github.com/russfellows/s3dlio/issues?q=is%3Aissue+151..157)**

This release supersedes v0.9.108 (v0.9.109 was an internal milestone, never separately published). It closes out a coordinated code audit that fanned out specialized reviewers across every backend and the Python DLIO integration layer, then adversarially verified every finding before it was allowed to count as a real bug. All 39 confirmed findings are fixed here, each with a dedicated regression test that was proven to fail against the old code and pass against the fix.

Full technical detail, the complete bug-by-bug table, and the full commit list: [`docs/Changelog.md`](../Changelog.md) and [PR #159](https://github.com/russfellows/s3dlio/pull/159).

## Why this release matters

If you use s3dlio for AI/ML data loading or checkpointing against S3, Azure Blob, GCS, or local/DirectIO storage, several of these fixes are things you were silently exposed to:

- **Correctness, not just hygiene.** Several bugs caused wrong *or missing* data with no error raised — a zero-byte object failing to download, a nested S3 key path getting silently flattened to just its filename, an Azure/GCS delete that reported success while an object was never actually removed. If your workload touches any of those code paths, upgrading changes real behavior, not just internals.
- **Fewer confusing failures.** A `S3DLIO_PUT_MAX_RETRIES=0` setting used to make every write fail immediately with "no attempts made" instead of using the documented default of 3. A transient HEAD-verification hiccup used to fail an otherwise-successful multipart upload. Both are now handled the way the docs always said they would be.
- **Config that was silently ignored now works, or is clearly labeled dead.** A handful of env vars had zero effect no matter what you set them to; the docs even quietly contradicted themselves about which ones worked. Both sides are now reconciled — see below.

## User-visible benefits

- **DLIO Python integration is safer end-to-end**: multipart writes now abort cleanly on failure instead of leaving a dangling upload; `walk_node()` preserves subdirectory structure instead of silently flattening keys; `create_node`/`delete_node`/`walk_node` no longer swallow real errors as `[]`/`True`/`False`; `AWS_ENDPOINT_URL` from your environment is no longer clobbered by DLIO's own endpoint selection.
- **`RangeEngine::download()` on a zero-byte object now succeeds** instead of erroring — matters for Azure/GCS backends and any workflow with legitimately empty files.
- **GCS reads are more resilient**: the retry loop now backs off exponentially instead of hammering a struggling endpoint, and a transient failure during RAPID-bucket detection no longer permanently poisons the cache with a wrong answer.
- **Azure multipart uploads fail fast and loud** instead of silently — a mid-upload failure now logs which blob and how many blocks were staged, and an object that would exceed Azure's 50,000-block limit is now rejected client-side with a clear, actionable error instead of wasting a full upload's worth of network I/O before failing server-side.
- **`direct://` (O_DIRECT) listing is fixed**: `list()` on a `direct://`-addressed store used to return `file://` URIs, so round-tripping them back through `store_for_uri()` silently lost O_DIRECT behavior. Now correctly round-trips.
- **URI/scheme detection edge cases fixed**: an Azure hostname check that could misroute a GCS key containing the right substring, and an `http://` Azure Blob URL that used to fail with a confusing "expected https://" error, both fixed.
- **`mp::Runner`'s HTTP-tuning builder methods actually work now** (`.max_http_connections()` / `.optimized_http()`) — previously silent no-ops.

## Environment variable changes

| Variable | What changed |
|----------|--------------|
| `S3DLIO_S3_ENDPOINT_TLS_PORTS` | **New.** Comma-separated list of additional ports to treat as TLS-terminated (`https`) for per-endpoint S3 clients addressed via `s3://host:port/...` — e.g. a load balancer terminating TLS on a non-standard port. |
| `S3DLIO_OPLOG_BUF` | **Behavior change.** Code default corrected from 256 to the documented 8192. If you rely on operation logging under bursty load, you'll drop far fewer entries than before. If you specifically depended on the old (undocumented, buggy) 256-slot behavior, set `S3DLIO_OPLOG_BUF=256` explicitly. |
| `S3DLIO_OPLOG_WBUFCAP` | **Docs-only fix.** Documented default corrected from 4096 to the actual code value, 262144 bytes (256 KiB). No code behavior changed. |
| `S3DLIO_PUT_MAX_RETRIES` | **Bug fix.** `=0` now correctly falls back to the documented default of 3, instead of producing a 0-attempt retry loop that failed every write. |
| `S3DLIO_MAX_HTTP_CONNECTIONS` / `S3DLIO_USE_OPTIMIZED_HTTP` | Still **not** read as env vars for direct usage (`s3-cli`, Python, etc.) — that hasn't changed. What's new: the Rust-only `mp::Runner` builder API's equivalent methods now translate into the real, wired vars (`S3DLIO_POOL_MAX_IDLE_PER_HOST`, `S3DLIO_ENABLE_HTTP2`) for its own spawned worker processes. If you were setting these as plain env vars expecting an effect, that still won't work — use `S3DLIO_POOL_MAX_IDLE_PER_HOST` / `S3DLIO_ENABLE_HTTP2` directly instead. |

Performance Tuning Guidelines in [`docs/Environment_Variables.md`](../Environment_Variables.md) were also corrected — they previously recommended exporting env vars that the docs' own "dead names" note declared had no effect.

## Behavior changes to be aware of

- **`parse_s3_uri_full` endpoint-detection heuristic narrowed.** An `s3://` URI's first path segment used to be treated as a custom endpoint hostname if it merely contained 2+ dots, started with a digit, or contained `minio`/`ceph`/`localhost` — misrouting legitimate bucket names shaped that way (e.g. `mycompany.data.backups`). If you relied on the old broad heuristic, add a port to your URI or set `S3DLIO_S3_ENDPOINT_HINT_TLDS`.
- **DLIO `round_robin` endpoint selection is now rank-based** (MPI/SLURM/PMI), not a static per-process PID hash.
- **DLIO storage `create_node`/`delete_node`/`walk_node` no longer swallow arbitrary exceptions.** If your code depended on these silently returning `[]`/`True`/`False` on real errors (auth failures, network errors), you will now see the exception instead.
